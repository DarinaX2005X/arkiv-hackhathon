# 02 Собрать выполнимый проект и получить согласие каждого
Status: todo

Канонический план, консолидирован MAIN. PROJECT/DESIGN/PROTOCOL и REQUIREMENTS являются авторитетными входами. Это ещё не назначение на реализацию и не журнал выполненной работы.

Этап делает проверяемым главное действие Partfolk: из реальных условий получить полный предложенный план, а затем собрать согласия его участников. Пользователь начинает с локального примера без кошелька, понимает конкретный пробел, меняет один вклад и получает другой результат. Для собственного проекта используются те же правила. Вычисленная совместимость, опубликованные данные и согласие людей остаются разными состояниями.

Общий контракт всех задач в этом документе:

- MAIN владеет `src/domain/types.ts`, всей общей моделью и контроллерами, `src/ui/`, `src/app/`, `src/i18n/`, зависимостями, общими scripts, Git и каноническими `.vibemachina/` файлами. Работники не создают вторые типы планов, собственный solver, отдельный wallet service или параллельный набор UI-токенов.
- UI получает repository, application controller, текущий режим и пользователя через общий контекст, поставленный в 01.1–01.3. SDK, RPC-запросы и правила авторства не помещаются в feature-компоненты. Имена экспортов согласуются с реальными общими контрактами перед назначением; интерфейс не заполняется временным сервисом с безусловным успехом.
- Записи относятся к **partfolk/1**, namespace **partfolk**. Старые рабочие названия Convene/Patchbay не входят в продукт, схемы, URL или экспорт. Точные записи/головы/решения разрешает общий domain layer; UI не выбирает «самую новую» конкурирующую запись по номеру на свое усмотрение.
- Любое материальное изменение пакета согласованного плана создает новую версию и требует нового согласия **всех** необходимых текущих участников. Прогресс исполнения, комментарий, фильтр экрана и неиспользованный новый вклад сами по себе план не меняют. UI не переносит незатронутые согласия на новую версию.
- Поиск вкладов существует в контексте конкретного проекта. Глобального `/explore`, общего маркетплейса и Communities CRUD нет. Отображаемая подпись организации не равна проверенной личности или праву действовать от имени реальной организации.
- Все заданные функции доступны на русском и английском, включая ошибки, формы, ожидание, accessibility names и экспортированные системные подписи. Feature-каталоги размещаются внутри своего exclusive path и подключаются MAIN к общей i18n-системе. Переключение языка не уничтожает черновик и не переводит пользовательский контент.
- Компоненты используют утвержденные токены и общие primitives. Длинные условия и русские кнопки переносятся; смысл не зависит только от цвета, hover или широкого экрана. Действие, которое меняет вклад или согласие, остается доступным с клавиатуры и touch.
- Первые полезные 30 секунд и первые пять минут являются целями пользовательского опыта до измерения. Никаких обещаний скорости по одному синтетическому fixture.
- Проверки ниже предполагают, что 01.1 установит общие команды `npm.cmd run typecheck`, `npm.cmd run test:unit -- <path>`, `npm.cmd run build` и `npm.cmd run build:desk`. Это планируемые команды, сейчас они не считаются существующими или пройденными. MAIN заменяет названия согласованно, если фундамент выберет другие. Feature unit tests colocated внутри принадлежащего задаче каталога.
- Работник передает MAIN связный проверенный increment и evidence; MAIN проверяет общие связи, читает весь TESTING и делает scoped checkpoint. Пользователь проверяет браузер и внешний вид. Агентам запрещены CUA, Playwright, Selenium, Puppeteer, headless browser, screenshots и аналогичный UI-рендеринг/автоматизация. Статические, unit, domain, server и HTTP/API проверки разрешены. Успешная сборка не является visual QA.

Depends on: 01.1, 01.2, 01.3

Пользовательский результат: человек открывает понятный локальный пример или создает свой проект, задает необходимые люди/место/оборудование и допустимые варианты, видит конкретный пробел или полные найденные планы, сравнивает их, выбирает один для согласования и возвращается к сохраненной работе. Задача покрывает проектное редактирование и предложение плана; публикация собственных вкладов и личные решения участников выполняются через 02.2, проведение через 03.1.

Граница записи: только `src/features/projects/`, включая компоненты, feature-specific presentation/selectors, каталоги RU/EN и значимые unit tests. Общий route registry, контекст, types, domain, UI primitives и package scripts остаются MAIN. Передать MAIN route exports для `/demo`, `/workspace`, `/projects/:id` и `/projects/:id/plans`; не создавать собственный вложенный router, если общий router уже предоставляет route context.

Входы: существующий локальный draft, открытый публичный project ID, fixture Small Works или новая форма. Минимальные поля: название, цель, часовой пояс, допустимые даты/конфигурации и требования. Для требования вводятся тип, название, количество с единицей и необходимый временной интервал. Значения должны соответствовать runtime schema: непустое назначение, положительное целое количество неделимых вещей/людей, начало раньше конца, определенная зона и допустимая дата. Не обрезать молча значение до максимума. Свободный текст условий помечается как примечание для людей, если общий domain layer не умеет его проверять.

Авторитетные результаты: сохраненный draft/project revision, solver result с исходной версией входов, найденные полные assignment sets либо объясненные gaps/conflicts, выбранный proposed plan. Сам feature не генерирует якобы существующих партнеров, не превращает предположение организатора в чужой offer и не ставит acceptance. Допущения локального планирования визуально отличаются от опубликованных владельцем предложений и не дают публичного статуса согласования.

Ключевые состояния: пустой собственный проект; редактируемый несохраненный draft; сохраненный локально; публикация ожидает пользователя; публикация/чтение не подтверждены; валидные и ошибочные требования; нет подходящих предложений; вычисление реально запущено; план невозможен; часть данных недоступна; найдено несколько планов; выбранный результат устарел после ввода; конкурирующие публичные состояния; найденный план передан на согласование. Старый результат остается виден как старый, но не может незаметно отправиться на согласование как текущий.

Переходы должны сохранять нужные данные: уход к вкладчику и назад, смена языка/режима, отмена wallet connection, обновление страницы и ошибка локального хранения. Данные одного аккаунта не восстанавливаются автоматически как draft другого. При невозможности local persistence прямо сказать, что черновик пока только в памяти, и дать реальный export. Повтор публикации идет через общий operation/reconciliation controller, а не по второму нажатию без проверки исхода.

## 02.2 Управлять своим вкладом и соглашаться только на конкретные условия
Status: todo

Depends on: 01.1, 01.2, 01.3

Paths: src/features/contributions/

Пользовательский результат: участник публикует собственное время, место или оборудование, видит запросы нескольких проектов и занятость, принимает или отклоняет точную версию полного плана, управляет доступностью и может отозвать обещание. До публикации он может подготовить данные локально; для реального авторства нужен поддерживаемый foundation wallet/session flow. Задача также дает повторно используемые feature views для independent Partner Desk в 03.2.

Exclusive ownership: `src/features/contributions/`, с feature catalogs и tests. Общий wallet/session/repository controller только потребляется. Существующие `src/ui/` primitives не копируются. Exported presentation components получают actor/mode/query state и commands через общий context либо совместимые injected props; они не требуют main application's router singleton или origin-specific local storage. Это нужно для normal Desk use, а не для декоративного «независимого» экрана.

Входы: invitation с project/revision context; новый или существующий own offer; внешняя ссылка на complete plan; новый confirmed/unconfirmed wallet actor. Offer содержит тип, название, количество/capacity, availability intervals, допустимые роли/использование и поддерживаемые условия. Чужое предложение доступно для чтения и выбора в плане, но его форма редактирования не открывается как собственная только из-за совпавшего display name.

Результаты: owner-authored offer revision, personal decision против exact plan revision, видимая реальная занятость по времени, текущие requests/accepted contributions и подтвержденный withdrawal/change. UI не обещает CAS/atomic reservation между независимыми клиентами. Если общий resolver обнаруживает конфликт, acceptance не превращает конфликт в зеленый ready state.

Состояния: нет предложений; local offer draft; invalid quantity/time; disconnected/connecting/connected wrong-network actor; ожидается wallet action; пользователь отказался; public write pending; unknown outcome; confirmed; новый account во время формы; чужой/недоступный/expired offer; proposal ждёт решения; decision declined/accepted/historical; offer changed и план stale; конфликт занятости; withdrawal pending/confirmed. Точные wallet/rpc причины находятся в contextual diagnostics, а центральный текст объясняет, что человек может сделать и что уже сохранено.
