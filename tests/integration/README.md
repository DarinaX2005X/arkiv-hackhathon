# Repository acceptance tests

These Node tests exercise the production repository, solver, agreement and feature-command contracts. They do not launch a browser, render the interface, contact Arkiv, sign transactions or claim live-network evidence.

Run from the repository root:

```sh
node node_modules/typescript/bin/tsc --noEmit -p tests/integration/tsconfig.json
node node_modules/vitest/vitest.mjs run --config tests/integration/vitest.config.ts
```

`custom-project.test.ts` starts with empty serialized storage. Independent `LocalRepository` instances create a new listening session, register previously unknown contributors, share offers, explicitly admit them, publish the complete proposal and its requests, and record each owner's separate decision. Its data differs from Small Works: three listening stations, one person in two adjacent roles, a different date and `Europe/Paris` time zone. It verifies complete assignments, canonical hash, exact missing-owner reasons, saved consent and export read-back. A one-millisecond schedule overlap must remain impossible with the chosen assignment pinned.

`repair-delta.test.ts` uses the real persisted guided actions to verify the exact Small Works repair explanation. Only Oak's transport and Cedar's installation are replaced by Cedar's transport and Juniper's installation. The other allocations remain equal, while every required owner has a missing decision on the new activation.

## Boundaries

The local custom-project test passes real serialized records between new repository instances. The independent-process test separately starts the production public runtime in isolated Node processes, supplies each one with its own storage and RPC port, and waits for process exit before starting the next client. Its Node lock adapter provides real process-local exclusion for that isolated storage. It does not launch the Desk interface, exercise browser cross-tab locking, use a private key, prove a wallet signature or contact a public network. Live transactions and independently queried public evidence have their own explicitly authorized runner under `tests/arkiv-live/`.

The user verifies visible explanations, discovery of the next action, role and revision review, keyboard/focus behavior, responsive layout, and visual/export appearance. A passing test here does not close those user-owned checks.

## Recovery and independent-client acceptance map

`competing-projects.test.ts` prepares both projects' decisions against the same owner book. Project 1 reserves a capacity-one projector while its other owner is still pending. Project 2's retained command fails with `stale_heads`; preparing it again from the current book returns `capacity_exceeded`. Only Project 1 can become Ready.

`independent-process.test.ts` exercises two real process boundaries against deterministic native RPC responses. First, the initial Studio reader exits, an independently configured Desk runtime withdraws its own commitment, and fresh Studio and CLI readers reconstruct the same authored record and exact agreement. HTTP is rejected before any request can leave the fixture, so no Studio API is available. Second, a publication process exits immediately after its serialized `proposal_confirmed` checkpoint is delivered. A fresh process restores only the saved journal and original command, reconciles the receipt, reuses the proposal and consumes exactly the former activation. Changed caller input cannot replace the retained command; the new activation still needs a new owner decision.

`read-failures.test.ts` drives the real SDK, repository and current-view controller. A query-level 429 immediately invalidates a previously Ready snapshot while preserving its last-known content, and a subsequent complete read restores confidence. An unavailable pinned historical block fails without switching to another block or returning partial data.

## Execution, closure and reuse acceptance

`execution-completion.test.ts` is one repository flow parameterized over three honest outcomes. Two owners agree to a custom printing table, record their tasks, confirm the handover of two trays, and report the return. The equipment owner acknowledges two, one, or zero returned trays. New repository instances then close and reload the project as `completed`, `completed_with_outstanding`, or `cancelled`. Each closure consumes its exact activation while preserving every owner's book unchanged. The latter two outcomes keep the remaining custody and unfinished return explicit; attempting full completion is rejected.

The same flow builds and parses the production JSON/HTML export text for proposed, Ready, unverified and closed states. Its unverified snapshot comes from an actual injected storage-read failure through the repository and current-view controller. Assertions retain the exact proposal/source/hash, time zone, recorded snapshot and outcome. This is local evidence with a null block number; the independent public process test separately checks its canonical block and matching verification packets. HTML is checked as file content only.

Finally the exported closure supplies `reuseRecipe` and the production editor validation. Dates are cleared before a later date is entered, the equipment requirement is removed, and a new saved project root begins with no admitted parties or execution history. Explicitly admitting the existing host's standing offer allows a new calculation and publication. The old host's consent does not count for the new activation, and the old equipment owner's outstanding custody remains untouched.

Existing mechanics are intentionally not repeated here: `src/domain/__tests__/local.test.ts` covers persisted quantity correction, the remaining-work publication and full return; `src/data/__tests__/arkiv-writer.test.ts` covers those same commands through native public write verification; `src/features/execution/execution.test.ts` covers retained completion after withdrawal, only-remaining-work repair, corrected statements and transfer statuses. The new parameterized flow supplies the previously missing persisted closure → export → new saved root boundary.
